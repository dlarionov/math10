# Облегчённый SDD

## Размер задачи определяет размер процесса

| Изменение | Достаточные документы |
| --- | --- |
| Опечатка, небольшой стиль, починка ссылки | Коммит с понятной причиной; новая спека не нужна |
| Ошибка в математике или проверке ответа | Исправление, независимый пример, проверка регрессии; обновление существующей спеки при изменении поведения |
| Новый урок или существенное изменение сценария | Один файл specs/NNN-topic.md по шаблону |
| Общая архитектура, хранение данных, публикация | Спека и запись решения; проверить границы разрешения пользователя |

Не создаём обязательные отдельные файлы plan/tasks/research для каждой задачи. План, вопросы и результаты проверки помещаем в спеку. Большой материал делим только когда это упрощает работу.

## 1. Восстановить контекст

Прочитать AGENTS.md, docs/SESSION.md и связанную спеку. Конституцию читать при первой работе в сессии; точечные справки — по необходимости. Проверить `git status` и текущую ветку. Чужие изменения не перезаписывать.

Перед синхронизацией проверить remote. Fetch безопасен; если появились удалённые коммиты, сначала изучить расхождение. Не делать pull с потенциальным перезаписыванием незакоммиченных файлов.

## 2. Описать результат

Сформулировать учебную цель, необходимые знания, основной вопрос, границы темы и наблюдаемые критерии приёмки. Описать интерактивные действия и ожидаемый результат. Для математических вычислений заранее подготовить несколько независимых примеров с ответами.

Разумные обратимые решения принимать самостоятельно и указывать в спеке. Обязательный неизвестный параметр уточнять, продолжая независимую работу. Статус «готова к реализации» не означает, что пользователь уже поручил реализовать эту тему.

## 3. Реализовать

Работать в рамках задачи. Обычная небольшая задача может выполняться в main; для большого или рискованного эксперимента использовать отдельную ветку. Не заводить ветки и worktree без практической пользы.

Сохранять самостоятельность уроков. Новую HTML-страницу добавлять в index.html и LESSONS.md. Существующие уроки менять только по связанным требованиям или ради необходимой совместимости.

У нового урока указывать содержательную связь с соседними темами и по возможности обратный переход; уточнять короткий маршрут в каталоге. Ссылки не заменяют необходимых определений и напоминаний внутри самостоятельной страницы. Для самих переходов достаточно обычных локальных ссылок, без обязательного прохождения.

## 4. Проверить

Выполнить `python3.12 scripts/check_project.py` и проверки, соответствующие изменению, из docs/QUALITY.md. Математические ответы сверить независимо. Для интерактивного урока нужны фактическое исполнение в браузере, проверка телефона, клавиатуры и состояний ошибки.

В спеке кратко записать команды, результат и оставшиеся ограничения. Не отмечать непроведённые проверки как успешные. Повторять проверки после изменения соответствующего кода, а не ради накопления отчётов.

## 5. Закончить и сохранить

Обновить статус спеки, реестр уроков и docs/SESSION.md. Значимое решение с последствиями добавить в docs/DECISIONS.md. Удалить собственные временные файлы и остановить свои фоновые процессы.

Просмотреть diff, исключить секреты и случайные файлы, сделать содержательный коммит и обычный push. Коммиты небольшие, но самостоятельные: например `docs: establish lightweight SDD` или `feat: add graph transformations lesson`. Русский язык описаний допустим.

Использовать нейтральную локальную identity из AGENTS.md. После stage выполнить `python3.12 scripts/check_privacy.py --staged`, после коммита и перед push — `python3.12 scripts/check_privacy.py --history main`. В публичную документацию не переносить переписку и личные результаты обучения.

Проверить успешность push и чистоту рабочего дерева. При отсутствии доступа сохранить локальные коммиты и прямо сообщить о непереданных изменениях; не переписывать историю ради обхода отказа. Push не равен публикации сайта.

## 6. Предложить продолжение

В конце сообщить, что изменилось, что проверено, что осталось. Предлагать новую сессию после завершённого урока или самостоятельного этапа; также когда длинная история мешает следующей работе. В docs/SESSION.md указать следующий шаг и короткий стартовый запрос.

Если задача ещё не завершена, сначала довести доступную работу до устойчивого состояния. Новая сессия — предложение родителю, а не требование и не утверждение о техническом лимите контекста.

## Статусы спецификаций

- **Черновик** — есть существенные открытые вопросы.
- **Готова к реализации** — цель и критерии определены; реализация ещё не началась.
- **В работе** — есть незавершённая реализация.
- **Реализована** — критерии проверены либо ограничения явно перечислены.
- **Исходная база** — описание существующего материала без заявления о полной приёмке.
- **Отложена** — решение сознательно перенесено, причина указана.
